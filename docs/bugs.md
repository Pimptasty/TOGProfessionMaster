## Active Issues — Messaging & Communications

- ⚠️ [MSG-001] 🔴 **HIGH** Incoming addon message without a colon separator crashes the message handler — `message-service.lua` parses the message prefix with `string.sub(message, 1, string.find(message, ":") - 1)`. When no colon is present in the message, `string.find` returns `nil`, and `nil - 1` throws `attempt to perform arithmetic on a nil value`, crashing `OnCommReceived` for that message. Any addon message sharing the `"PmV1"` registered prefix without the colon separator — whether malformed or malicious — will trigger this crash. This is also a minor denial-of-service vector: an attacker with another addon using the same prefix could freeze the handler. Fix: Add a guard `local pos = string.find(message, ":"); if not pos then return; end` before the subtraction. Location: `services/message-service.lua` prefix parsing (~line 33).

- ⚠️ [MSG-002] 🟠 **MEDIUM** `lastHandledMessage` deduplication flag is never cleared, silently dropping repeated messages for the entire session — `chat-service.lua` sets `self.lastHandledMessage = messageKey` to deduplicate duplicate rapid-fire messages, but the field is never reset, expired, or rotated. If the same player sends identical message text twice in a session (e.g., two `/pm who ItemName` queries for the same item), the second message is silently ignored for the remainder of the game session, not just for a brief duplicate-suppression window. Fix: Clear `self.lastHandledMessage = nil` after handling, or expire it with a short `C_Timer.After` TTL. Location: `services/chat-service.lua` message deduplication (~line 171).

- ⚠️ [MSG-003] 🔴 **HIGH** Malformed incoming profession sync message with missing field crashes in `gmatch` — `player-professions-message.lua` indexes `values[4]` directly to get the skills string without first checking that the split produced at least 4 parts. If an incoming guild message is truncated, corrupted, or missing fields, `values[4]` is `nil`. The call `messageService:SplitString(nil, ",")` passes `nil` to `string.gmatch`, throwing `bad argument #1 to 'gmatch' (string expected, got nil)` and crashing the sync receive path. Fix: Add a length guard `if #values < 4 then return; end` before indexing `values[4]`. Location: `models/messages/player-professions-message.lua` skill string parsing (~line 45).

- ⚠️ [MSG-004] 🟠 **MEDIUM** Skill entry without a dot separator leaves `itemId` as `nil` instead of `0`, causing incorrect downstream nil checks — `player-professions-message.lua` splits each skill part on `.` and calls `tonumber(skillParts[2])` for the item ID. If a skill entry in the message has no `.` separator (malformed message), `skillParts[2]` is `nil` and `itemId = tonumber(nil) = nil`. The resulting `{skillId = ..., itemId = nil}` record is passed to `StorePlayerSkills`, where guards like `skill.itemId ~= 0` evaluate `nil ~= 0` as `true` and run branches that should not execute. Fix: Default `itemId` to `0` when `skillParts[2]` is absent: `local itemId = tonumber(skillParts[2]) or 0`. Location: `models/messages/player-professions-message.lua` skill part parsing (~line 47).

## Active Issues — Data Management

- ⚠️ [DATA-004] 🔴 **HIGH** `GetSpellCooldown` returns a bogus `start` value for profession cooldowns on some clients, causing wildly inflated remaining times (e.g. "50d 23h" instead of "1d 6h") — root cause not yet confirmed; the symptom affects both transmute spells (e.g. Transmute: Water to Air) and regular spell-based cooldowns (e.g. Mooncloth). The best hypothesis is that `GetSpellCooldown` returns a `start` expressed in `GetServerTime()` (Unix) units on some Classic Era patch levels rather than `GetTime()` units, making the `(start + duration) - GetTime()` calculation produce a value close to Unix epoch seconds. A `/pm debug cooldowns` command was added in v1.1.1 and improved in v1.1.2 to capture the raw `start`, `duration`, `remaining`, and stored `expiresAt` values in chat for diagnosis; v1.1.2 also prints every tracked spell ID with its `IsSpellKnown` status regardless of whether a cooldown is active, exposing any IDs missing from the tracked list. **Second observed symptom (v1.1.2):** A tester with a transmute-specced Alchemist ran `/pm debug cooldowns` and saw only the two header lines with no transmute entries at all — the stored section showed `(no stored entries)`. This means `IsSpellKnown` returned `false` for every ID in `GetTransmuteIds()`, so the "Ready" seed never fired. The player may know a transmute spell whose ID is not yet in our list, or `IsSpellKnown` may behave differently on their build. Investigate by examining which IDs printed `known=false` vs `known=true` in their debug output and cross-referencing against `models/cooldown-ids.lua`. Mitigations applied: (1) sanity cap — computed `remaining > 30 days` is discarded at the scan site for both transmute and regular cooldowns, and for incoming broadcast messages; (2) auto-fixup — if a stored `expiresAt` is more than 30 days in the future and no valid active CD is found by `GetSpellCooldown`, the entry is immediately reset to "Ready". These mitigations prevent bad data from displaying but do not fix the underlying cause — a correct CD duration will also be silently dropped if it exceeds the cap. Fix: determine actual units returned by `GetSpellCooldown` on affected builds (via debug output from testers), and verify complete transmute spell ID coverage in `models/cooldown-ids.lua`. Location: `services/cooldowns-service.lua` `ScanTransmuteCooldown()` and `ScanLocalCooldowns()`; `services/commands-service.lua` debug handler.

- ⚠️ [DATA-003] 🔴 **HIGH** Migration guard always evaluates false; pre-v7 users silently lose all saved profession data — `TOGProfessionMaster.lua`'s `Migrate()` function reads `TOGPM_Settings.storeVersion` to decide whether to run the v7 data migration. ## Active Issues — Version Detection

- ⚠️ [VER-001] 🟠 **MEDIUM** Version detection uses unanchored Lua pattern with a wildcard dot, fragile against future Classic version strings — `TOGProfessionMaster.lua` detects game version with `string.find(wowBuild, "1.") == 1` (and similarly for `"2."`, `"3."`, `"4."`, `"5."`). In a Lua pattern, `.` matches any character, not a literal dot. More critically, a future Classic version string beginning with `"10."` (e.g., a 10th-anniversary era client) would match the `"1."` pattern and incorrectly set `isVanilla = true`. The plain-text fourth argument (`true`) that would disable pattern matching is absent. Fix: Use anchored, escaped patterns: `string.find(wowBuild, "^1%.")` for each branch. Location: `TOGProfessionMaster.lua` version detection block (~lines 42–46).

- ✅ [VER-002] ~~🟠 **MEDIUM** Unpackaged development builds carry the literal `"@project-version@"` string, causing nil arithmetic crashes in version comparisons~~ **FIXED (April 15, 2026): Root cause was broader than originally documented — packaged releases use a tag like `TOGProfessionMaster-v1.1.0` which also fails `tonumber()` on the first dot-segment. Fixed by replacing the raw `string.gmatch`/`tonumber` loops in `Initialize()`, `OwnIsLower()`, and `OwnIsHigher()` with a new `ParseVersionParts()` helper that strips any non-numeric prefix (`string.match(v, "(%d[%d%.]*)")`) before splitting on `.`, and returns `{0,0,0}` for unparseable strings (dev tokens). Both own and peer version strings now pass through the same helper, so all formats are handled robustly.
